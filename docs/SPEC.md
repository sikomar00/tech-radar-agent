# Spec v1.6

기준: `docs/PRD.md`, `docs/ERD.md`, `docs/adr/`. 1단계는 구현할 수 있는 수준으로 쓰고, 2단계는 중복 탐지와 후보 선별만, 3단계는 확정된 것만 적는다. 4~6단계는 PRD 원칙(게이트 통과 전에는 다음 단계를 시작하지 않는다)에 따라 각 단계 시작 전에 추가한다.

## 1단계 · 수집 엔진

### 어댑터 인터페이스 (S1-01)
- 어댑터는 `fetch(source) -> FetchResult`를 구현한다. `FetchResult`는 항목 목록과 요청별 결과(성공 또는 실패와 원인)를 담는다.
- 항목(`RawItem`)은 `external_id`(없으면 null), `url`, `title`, `excerpt`, `published_at`(없으면 null), `metadata`를 가진다.
- 어댑터는 DB를 모른다. HTTP 호출은 주입받고, 응답을 `RawItem`으로 바꾸는 일만 한다.
- 요청 사이는 1초 쉬고, 타임아웃은 20초, 요청마다 식별 가능한 User-Agent를 보낸다. 요청 단위 재시도는 하지 않는다. 성공률을 요청 단위로 세기 때문에 실패를 숨기지 않기 위해서다. 재시도는 잡 단위로 한다.

### 소스별 동작 (스파이크에서 동작을 확인한 방식)
| 소스 | 가져오는 것 | `external_id` | 비고 |
| --- | --- | --- | --- |
| GitHub 신규 저장소 | 검색 `created:>{7일 전} stars:>20`, 스타순 30건 | 저장소 숫자 id | metadata에 스타, 언어, 토픽, archived, fork, 생성·푸시 시각 |
| GitHub 릴리스 | 시드 저장소별 최근 3건 | 릴리스 id | 제목은 `owner/repo tag`. 시드 목록은 `sources.config` |
| Hacker News | 공식 API의 topstories와 showstories 각 15건 | 글 id | URL이 없는 글은 HN 글 주소를 URL로 쓴다. dead·deleted는 건너뛴다 |
| RSS | 피드의 최근 항목 | guid(없으면 null) | 발췌가 없으면 빈 문자열을 허용한다 |

### 정제 (S1-03, S1-06)
- 제목은 300자, 발췌는 280자에서 자르고(DB 상한은 500자) 공백과 제어 문자를 정리한다. 본문 전문은 저장하지 않는다.
- 엔티티를 풀고 태그를 지우는 것은 HTML이 올 수 있는 필드(RSS 요약, HN 글 본문)에만 한다. 제목이나 GitHub 설명 같은 일반 텍스트는 태그를 지우지 않는다(`Vec<T>`가 깨지면 안 된다). HN 제목은 엔티티만 푼다.
- `normalized_url` 규칙은 `host/path?정렬된 쿼리` 형태다.
  1. 스킴(http, https)은 지운다.
  2. 호스트는 소문자로 바꾸고, 앞의 `www.`와 기본 포트를 지운다.
  3. 프래그먼트(`#...`)를 지운다.
  4. 추적 파라미터(`utm_*`, `fbclid`, `gclid`, `mc_cid`, `mc_eid`)를 지우고 나머지 파라미터는 키 순으로 정렬한다.
  5. 경로 끝의 `/`를 지운다(루트 제외). 경로의 대소문자는 유지하지만 `github.com` 경로는 소문자로 바꾼다.
- 위 규칙은 일반 관행에 따른 가설이다. 스파이크 표본에는 정규화가 필요한 변형 사례가 없었다. 새 변형이 나오면 fixture를 추가하고 규칙을 고친다.
- `content_hash`는 소문자로 바꾸고 공백을 정리한 `제목 + "\n" + 발췌`의 SHA-256이다. 발췌가 비어 있으면 `normalized_url`을 이어 붙여서, 제목만 같은 서로 다른 글이 한 항목으로 합쳐지지 않게 한다(Hugging Face 피드가 이 경우다).

### 저장과 중복 방지 (S1-02, S1-04)
- 항목마다 `(source_id, external_id)` → `normalized_url` → `content_hash` 순으로 기존 행을 찾는다.
- 못 찾으면 새로 넣는다. 찾았을 때는 **같은 항목인지** 먼저 본다. 찾은 행의 `source_id`와 `external_id`가 모두 같을 때만(둘 다 `external_id`가 없는 경우 포함) 같은 항목으로 보고 제목, 발췌, metadata, `collected_at`을 갱신한다(`first_discovered_at`은 유지). 그 밖의 경우, 곧 다른 소스가 이미 가진 URL이거나 같은 URL·같은 텍스트를 가리키는 서로 다른 항목이면 행을 건드리지 않고 `duplicates`로 세고 로그에 남긴다. 덮어쓰면 소스끼리 제목이 번갈아 바뀌기 때문이다. 대신 같은 URL을 가리키는 서로 다른 항목(예: 모든 글이 같은 페이지로 링크하는 변경 로그 피드)은 첫 항목만 남는다. ERD의 `normalized_url` 전역 유일 제약의 결과다.
- 빈 `external_id`는 없는 것으로 본다. 제어 문자는 `url`과 `external_id`에서도 지운다.
- GitHub의 `external_id`는 `repo:<id>`, `release:<id>`다. 저장소 id와 릴리스 id는 서로 다른 번호 공간이라 접두사가 없으면 같은 숫자가 한 행으로 합쳐질 수 있다.
- 갱신은 키(`external_id`, `normalized_url`, `content_hash`)와 `url`을 바꾸지 않으므로 제약과 충돌하지 않는다. 그 대신 GitHub 저장소 이름이 바뀌면 `url`이 옛 이름을 가리킨다(알려진 한계, 2단계에서 필요해지면 충돌 처리와 함께 갱신한다). 삽입 중에 키 충돌이 나면(조회 직후 다른 쓰기가 끼어든 경우뿐) 그 항목을 건너뛰고 `conflicts`로 센다. 저장할 수 없는 항목(호스트 없는 URL, 인코딩할 수 없는 문자)도 건너뛰고 `invalid`로 센다. 이 개수들은 실행 로그에 남기고 `collection_runs`에는 저장하지 않는다.
- `published_at`은 소스가 준 최초 공개 시각이고, `first_discovered_at`은 우리가 처음 저장한 시각이다. 둘은 다른 값이다.
- GitHub 항목은 스타 수 스냅샷(`metadata.stars_snapshots`, 최근 10개의 `{at, stars}`)을 이어 붙여 둔다. 2단계의 스타 증가율 계산에 쓴다. 스키마 변경은 없다.

### 잡, 워커, 스케줄 (S1-05, S1-07)
- 워커는 1개이고 루프는 다음 순서다.
  1. 스케줄: 활성 소스마다 마지막 실행 뒤 `collect_interval`이 지났고 `queued`나 `running` 잡이 없으면 `collect_source` 잡을 만든다.
  2. 잡 하나를 `FOR UPDATE SKIP LOCKED`로 가져와 실행한다.
  3. 성공하면 `succeeded`로 한다. 실패하면 `2^attempts`분 뒤로 `run_after`를 미루고 다시 `queued`로 둔다(`attempts`는 잡을 가져올 때 올린다). `max_attempts`(3)를 다 쓰면 `failed`로 남긴다.
  - 잡은 요청이 **모두** 실패했거나 예외가 났을 때만 실패다. 일부 요청만 실패하면 성공한 항목을 저장하고 잡은 성공으로 끝내며, 실패한 요청은 `collection_runs`의 `requests_failed`와 `error`에 남긴다(실패한 요청을 즉시 재시도해도 같은 원인일 가능성이 커서 요청을 더 늘릴 뿐이라서다).
  4. `locked_at`이 15분 넘은 `running` 잡은 시도 횟수가 남았으면 `queued`로 되돌리고, 다 썼으면 `failed`로 둔다.
- 기본 수집 주기는 GitHub 6시간, Hacker News 1시간, RSS 1시간이다(초기값).
- `collection_runs`는 잡 시도마다 1행이다. `requests_total`, `requests_failed`, 그리고 `error`에 원인 분류(`http_status`, `timeout`, `network`, `parse`, `rate_limited`)와 메시지를 적는다.
- 소스별 성공률은 `(requests_total - requests_failed) / requests_total`이다. HTTP 2xx가 아닌 응답, 타임아웃, 연결 오류(연결 끊김, SSL 오류, 본문이 약속한 길이보다 짧게 끊긴 경우 포함), 파싱 실패는 실패로 세고, 200 응답에 결과가 0건인 경우는 성공으로 센다.
- 예외로 끝난 실행(어댑터 오류, 저장 오류)은 이미 보낸 요청에 **실패 1건을 더해서** 기록한다. 0건으로 적으면 성공률 분모에서 빠져 지표가 부풀려지기 때문이다. 워커가 죽어서 끝나지 못한 실행은 다음 정리 때 요청 1건 실패로 닫는다(`worker_died`). 소스가 없거나 페이로드가 잘못된 잡은 다시 해도 소용없으므로 재시도 없이 바로 `failed`로 둔다.
- 수동 재실행은 `radar jobs retry <job_id>`, 실행 기록 조회는 `radar runs list`다. 둘 다 운영용 명령이고 화면이 아니다.

### 1단계 시험 (게이트와 대응)
- 어댑터마다 실제 응답을 줄여 저장한 fixture 테스트.
- `normalized_url`과 `content_hash` 단위 테스트.
- 같은 입력을 두 번 수집하면 새 행이 0개다.
- DB 제약 테스트와, 워커의 재시도·잠금 복구 테스트.

## 2단계 · 기술 식별 (승인 2026-11-05)

기준: PRD S2-01~S2-07, ADR-0001·0004·0005, ERD의 `technologies`, `technology_aliases`, `analysis_runs`, `technology_sources`. 화면은 없고 운영 명령(CLI)만 있다. 2026-11-05 사용자가 이 절과 아래 "승인 시 함께 확인할 가정" 5~10번을 승인했다. 2단계 코드는 1단계 게이트를 통과한 뒤에 시작한다.

### 흐름
1. 스케줄러는 사전 필터를 통과했고, 현재 `classify` 결과가 없고, 대기·실행 중인 잡이 없는 수집 항목마다 `analyze_item` 잡을 만든다. 잡 종류는 `jobs.kind` 문자열이라 마이그레이션이 필요 없고, 같은 큐와 재시도 규칙(최대 3번, `2^attempts`분)을 쓴다.
2. 잡 하나는 분류 호출 1번(`kind=classify`)이다. 후보(ENTITY 또는 UPDATE)면 이어서 매칭(`kind=match`)과 기술 연결까지 한다.
3. 모든 호출은 `analysis_runs`에 쌓는다(S2-05). 성공한 새 결과가 생기면 같은 항목의 이전 `is_current`를 내리고 새 행을 올린다(한 트랜잭션). 행을 고치거나 지우지 않는다.
4. 입력 해시는 프롬프트 버전, 스키마 버전, 모델, 정제된 입력을 합쳐 만든다. 해시가 같은 성공 결과가 있으면 다시 호출하지 않는다. 무료 한도를 아끼기 위해서다.

### 사전 필터 (S2-01)
- 처음에는 제외 규칙 없이 모든 항목을 통과시킨다. 하루 호출 상한(375회)이 하루 새 항목 수(첫 측정 구간에서 수십~백여 건으로 추정, 24시간 측정으로 다시 확인)보다 크기 때문이다. 점수 같은 임계값을 먼저 걸면 후보를 놓친다. 골든셋 초안에서 Hacker News 13점짜리 모델 출시(ERNIE 5.5)가 후보였다.
- 제외 규칙은 튜닝용 골든셋에서 후보 Recall을 떨어뜨리지 않는 것만 추가한다(예: fork 저장소). 일일 상한에 걸리기 시작하면 그때 신호 기반 규칙(스타 증가율, 토픽, 키워드, 릴리스 여부, Hacker News 점수)을 넣고, 임계값은 튜닝용으로 정하고 보류용으로 검증한다(S2-07).

### 분류 호출 (`kind=classify`)
- 입력: 소스 종류, 제목, 발췌(280자), 소스별 메타데이터(GitHub의 스타·언어·토픽, Hacker News의 점수). 전부 구분자로 감싼 데이터 구간에 넣고, 도구 정의는 보내지 않는다(ADR-0004).
- 출력 스키마(평평하고 모든 필드 required): `class`(ENTITY, UPDATE, USAGE, NEWS, OPINION, NOISE), `canonical_name`(영문 정규명), `type`(PRODUCT, FRAMEWORK_LIBRARY, NONE. 3단계부터 PROTOCOL_STANDARD, MODEL 추가), `aliases_en`, `aliases_ko`(각각 문자열 목록, 최대 5개), `reason`(그 분류를 고른 이유 한 줄, 한국어, 100자. 2026-11-09 추가, 화면의 리스팅 이유에 "AI 판단"으로 보인다. 이전에 분류된 글은 비어 있다).
- 후보가 아니면 이름, 유형, 별칭은 버린다. 시험 호출에서 모델이 NOISE에 `none`을 채웠다.
- 이름 규칙: 저장소나 패키지 이름이 아니라 제품·프로젝트 이름을 정규명으로 한다. 모노레포 패키지 릴리스(예: `langchain-core`)는 프로젝트(LangChain)의 이벤트이고 패키지 이름은 별칭이다(ADR-0001). PRODUCT와 FRAMEWORK_LIBRARY가 아니거나 판단이 어려우면(모델 등) `NONE`이다.

### 기존 기술 매칭 (`kind=match`, S2-04)
세 단계다.
1. 규칙: 정규명이 대소문자 무시로 일치하거나, 같은 GitHub 저장소가 이미 `technology_sources`로 연결돼 있으면 같은 기술로 확정한다(하나로 좁혀질 때만. 여럿이면 모호하므로 아래 단계로 보낸다). **별칭이 같다는 것만으로는 확정하지 않는다.** 별칭은 모델이 낸 값이라 악의적인 글이 아직 없는 제품명을 별칭으로 심을 수 있고, 그러면 나중에 그 이름의 진짜 글이 잘못 합쳐진다. 별칭이 정확히 같은 기술은 유사도 1.0의 후보로 다음 단계에 올라가 모델이 판정한다(2026-11-06 사용자 승인으로 v1.2의 "정규명이나 별칭"을 바꿨다).
   - 자동으로 더하는 별칭은 다른 기술의 정규명·별칭과 겹치지 않는 것만 넣고, 후보 설명에 싣는 별칭은 기술당 10개까지다.
2. 퍼지: `pg_trgm` 유사도 0.6 이상(초기값, 튜닝 대상)인 후보 중 상위 5개만 다음 단계로 보낸다. 후보가 없으면 LLM을 부르지 않고 다른 기술로 본다.
3. LLM 판정: 새 항목과 후보 5개(id 포함)를 주고 `decision`(SAME, DIFFERENT, UNKNOWN)과 `technology_id`를 받는다. `technology_id`가 후보 목록에 없으면 모델이 만들어 낸 값이므로 저장하지 않고 실패로 기록한다.

### 기술 만들기와 연결
- SAME: 기존 기술에 `technology_sources`로 연결하고, 새 별칭은 `technology_aliases`에 더한다(중복 없음).
- DIFFERENT: 새 `technologies` 행을 만든다. `type`이 NONE이면 NULL로 두어 분류 보류가 된다. UPDATE인데 기존 기술이 없어도 같은 방식으로 새 기술을 만든다(그 기술이 처음 수집된 경로일 뿐이다). 소문자 정규명 유일 제약에 걸리면(동시에 처리된 경우) 새로 만들지 않고 기존 기술로 연결한다.
- UNKNOWN: 기술을 만들지 않고 항목을 보류로 둔다.
- `evidence_type`은 GitHub 릴리스 `release`, GitHub 저장소 `official`, ENTITY인 글 `announcement`, 그 밖은 `mention`이다. `confidence`는 항상 기본값 `Unverified`(미확인)다. AI 결과가 확인을 대신하지 않는다(PRD 원칙).

### 분류 보류 큐 (S2-03)
- 보류는 상태다. `technologies.type`이 NULL이거나, 현재 `match` 결과가 UNKNOWN이고 아직 연결되지 않은 항목이다.
- 운영 명령 4개: `radar holds list`(보류 목록과 모델 판단), `radar holds set <technology_id> <PRODUCT|FRAMEWORK_LIBRARY>`(유형 지정), `radar holds link <source_item_id> <technology_id>`(기존 기술에 연결), `radar holds new <source_item_id>`(새 기술로 만들기). 화면은 3단계에서 만든다.

### 실패와 한도 (ADR-0004)
- 실패한 호출은 `analysis_runs`에 `failed`와 `retryable`로 기록한다. 429, 503, 시간 초과, 네트워크 오류는 재시도 가능이다. 스키마 위반과 후보 목록에 없는 id도 재시도 가능으로 기록하되, 잡 시도 횟수(3번) 안에서만 다시 한다. 그 뒤에는 `failed`로 남고 `radar jobs retry`로 수동 재실행한다.
- 하루 호출 상한(375회, 분당 10회 이하)에 닿으면 호출하지 않고 잡을 다음 날로 미룬다. 이는 실패도 아니고 시도 횟수도 쓰지 않는다. 실패한 호출도 하루 횟수에 센다. 하루는 공급자 기준(태평양 시간 자정)으로 가른다.

### 평가 (S2-07)
- `radar eval`은 골든셋 CSV에서 `reviewed=Y`인 줄만 실제 모델로 돌려 후보 Precision·Recall, 유형 분류 정확도, 기존 기술 매칭 Precision, 중복 기술 생성률을 튜닝용과 보류용으로 나눠 출력한다. 임시 스키마에 항목을 하나씩 처리해서 같은 정규명의 항목이 한 기술로 모이는지 본다. 보류용 결과는 게이트 판정 때만 본다.
- 골든셋 100건을 한 번 돌리면 하루 호출의 20%를 쓴다. 입력 해시가 같으면 다시 호출하지 않으므로 프롬프트를 고쳤을 때만 새로 부른다. 평가하는 동안 운영 워커는 멈춘다.

### 2단계 시험 (게이트와 대응)
- LLM 호출은 `radar/llm/` 인터페이스 뒤에 있으므로 단위·DB 시험은 가짜 클라이언트로 한다(네트워크 없음).
- 시험 항목: 스키마를 어기는 출력, 후보에 없는 id, 429·503·시간 초과의 재시도 가능 기록, 한도 도달 시 미루기, 같은 입력 재처리 시 재호출 없음, `is_current` 교체, 소문자 정규명 충돌.
- 지시문 fixture(`tests/fixtures/injection/`): 제목·발췌에 지시문을 심은 항목. 가짜 클라이언트 시험에서는 요청 본문에 `tools`가 없고 스키마를 벗어난 출력이 저장되지 않음을 확인한다. 실제 모델에 대해서는 `radar eval`에서 위반 수를 센다.

### 후보 판별 기준 (2026-11-05 결정)
- 후보는 분류가 ENTITY 또는 UPDATE인 항목이다. USAGE, NEWS, OPINION은 기술을 언급해도 후보가 아니다.
- ENTITY와 UPDATE는 개발자·AI 실무자가 만들거나 연동하는 데 쓰는 도구, 라이브러리, 에이전트 도구, 모델, 표준만 해당한다. **용도로만 판단한다**(2026-11-08 결정, 이전에는 "개인용 앱·취미 프로젝트는 NOISE"): 작은 개인 프로젝트라도 개발자가 쓰는 것이면 후보이고, 일반 사용자용 앱·게임·에뮬레이터·홍보 글은 NOISE다.
- 애매하면 후보로 둔다(Recall 우선, 2026-11-08 결정). 게이트 목표는 Recall 85%, Precision 75%다.
- 2단계 유형은 PRODUCT와 FRAMEWORK_LIBRARY다. 모델 릴리스는 MODEL 유형이 3단계에 열리므로 유형을 비워 분류 보류 큐로 보낸다. 보류 큐에 모델이 너무 많이 쌓이면 2단계 측정 때 MODEL을 앞당길지 다시 묻는다.

## 3단계 · 지식 데이터베이스 (승인 2026-11-08)

기준: PRD S3-01~S3-09와 3단계 게이트, `docs/IA.md` v1.0, `docs/USER-JOURNEY.md` v1.0, ADR-0005·0006·0007, ERD의 3단계 테이블. 3단계 코드는 이 절과 Plan v3.0을 승인받은 뒤에 시작한다.

### 마이그레이션 0003
- DDL v1.1의 3단계 부분을 그대로 옮긴다: enum `knowledge_state`·`date_precision`, `users`, `technology_claims`, `claim_evidence`, `technology_events`(수정·삭제 금지 트리거 포함), `user_knowledge`, `user_notes`. 모두 정책 없는 RLS를 켠다.
- `sources.kind`에 `manual`을 더하고, 이름 `manual`인 비활성 소스 한 행을 넣는다(수집 스케줄에 잡히지 않는다).
- 사용자 한 명의 `users` 행을 넣는다. 웹과 CLI는 이 한 행을 쓴다(ADR-0006).

### 수동 등록 (S3-06, UJ-6)
- `radar add <url>`과 `radar add --file urls.txt`는 URL마다 공식 페이지 읽기(ADR-0007의 안전 규칙 그대로)로 `<title>`과 설명 메타 태그를 얻어 `manual` 소스의 수집 항목으로 저장한다. 중복 방지 규칙은 1단계와 같다(이미 있는 URL이면 그 항목을 쓴다).
- 사용자가 직접 넣은 것이므로 분석 잡에서 후보 판별을 건너뛰고 ENTITY로 다룬다. 이름·유형·별칭은 분류 호출로 받는다.
- 읽기가 실패하면(차단, 시간 초과) URL만으로 항목을 만들고 제목은 URL로 둔다. 결과는 URL마다 한 줄로 출력한다.

### 프로필 생성 (S3-01, S3-03, ADR-0007)
- 새 기술(보관 아님)이 생기면 `profile_technology` 잡을 만든다. 잡 우선순위는 수집 → 분석 → 프로필이고, 하루 호출 상한 375회를 함께 쓴다.
- 잡은 공식 페이지 한 장을 읽고(README 또는 대표 출처), 호출 1번(`kind=profile`)으로 8개 칸을 받는다: 한 줄 설명, 상세 설명, 해결하려는 문제, 주요 특징, 기존 기술과의 차이, 활용 사례, 장점과 한계(모두 한국어 문자열, 근거가 없으면 빈 문자열). 공식 출처 칸은 모델이 아니라 읽은 페이지의 URL로 채운다.
- 빈 칸은 행을 만들지 않는다. 행이 없는 칸이 "미확인"이다(ERD 가정 4). 채운 칸은 `technology_claims`에 `confidence=Unverified`로 넣고, 읽은 페이지에 대응하는 수집 항목을 `claim_evidence`로 잇는다. 다시 만들면 같은 칸의 이전 행은 `is_current`만 내린다.
- 페이지를 못 읽으면 제목·발췌만으로 한 줄 설명만 요청하고, 나머지는 미확인으로 둔다. 실패는 분석과 같은 규칙으로 `analysis_runs`에 남긴다.

### 변화 이력 (S3-04)
- 규칙으로만 만든다(AI 없음). GitHub 릴리스 항목이 기술에 연결되면 `release` 이벤트(발행 시각, 근거 키는 태그)를, GitHub 저장소 항목이 연결되면 `first_published` 이벤트(저장소 생성 시각, 근거 키는 저장소 URL)를 넣는다. 같은 이벤트는 unique 제약이 막는다.
- 인수, 통합, 지원 종료 이벤트는 글에서 뽑아야 해서 AI가 필요하다. 3단계에서는 만들지 않고 4단계(S4-07, 이벤트와 관계 연결)와 함께 연다(2026-11-08 사용자 결정으로 PRD S3-04 범위를 줄임).
- `technologies.first_published_at`은 `first_published` 이벤트에서 다시 계산한다.

### 유형 넓히기 (S3-09)
- 분류 지시문과 스키마의 유형에 PROTOCOL_STANDARD와 MODEL을 더한다. 이미 분류한 항목은 다시 분석하지 않는다.
- 유형이 빈 기술만 `radar holds retype`으로 한 번 더 묻는다(기술 이름과 연결된 출처 제목 최대 5개, 호출 1번). 이미 유형이 있는 기술은 건드리지 않고, 결과는 `analysis_runs`(`kind=retype`)에 남는다.

### 보관 (IA-3, UJ-5)
- "보관"은 `archived_at`을 채우고 "되돌리기"는 비운다. 보관한 기술은 Feed·검색·퍼지 후보에서 빠진다.
- 새 글의 정규명이 보관한 기술과 같으면 새 기술을 만들지 않고 그 보관 기술에 출처로만 잇는다(2026-11-08 결정). 같은 이름의 보관 기술이 여럿이면 가장 최근 것에 잇는다. 되돌리기 할 때 같은 이름의 활성 기술이 이미 있으면 되돌리지 않고 이유를 보여 준다(소문자 정규명 유일 제약).

### 검색 (S3-07, IA-2)
- 기술명·별칭은 대소문자 무시 부분 일치와 `pg_trgm` 유사도로, 키워드는 현재 프로필 주장 본문의 부분 일치로 찾는다. 결과는 기술 단위로 한 줄이다.
- 필터는 유형, 출처 종류(github, hackernews, rss, manual), 기간(최초 발견 시각), 내 상태다.

### 웹 화면 (S3-08, ADR-0006, IA v1.0)
- `radar web`이 `127.0.0.1:8765`에서 연다. 화면과 주소는 IA를 따른다. Feed의 "업데이트"는 기존 기술에 새 출처가 붙은 것이고, 같은 기술의 같은 날 출처는 한 줄로 묶는다. Feed 위에는 마지막 수집이 3시간 넘게 없으면 경고를 띄운다(UJ-1).
- 안전 규칙. 이 PC에서만 열려도 다른 웹사이트가 브라우저를 통해 `localhost`로 요청을 보낼 수 있다.
  - 요청의 `Host`가 `127.0.0.1:8765`나 `localhost:8765`가 아니면 거절한다(DNS 리바인딩 방어).
  - 바꾸는 요청(POST)은 `Origin`이 같은 주소일 때만 받는다(CSRF 방어).
  - 템플릿은 자동 이스케이프를 켜고, 외부 글의 링크는 `http`·`https`만 링크로 만든다(`javascript:` 차단).
- 내 상태·중요도·메모, 보관·되돌리기, 보류 처리(유형 지정·기존 기술에 연결·새 기술로), 실패 잡 다시 실행은 POST 폼으로 한다. 보류 처리는 `radar holds`와 같은 함수를 쓴다.
- 메모는 AI 내용과 다른 칸에 보이고, AI 분석은 `user_notes`·`user_knowledge`를 쓰지 않는다(S3-05).
- Feed·검색 줄과 상세의 출처 목록에 "리스팅 이유" 칸을 둔다(2026-11-09 결정): 분류 결과와 출처 신호(GitHub 스타, 릴리스 태그, HN 점수, RSS 발행처)로 만든 규칙 근거와, 분류 호출의 `reason`(AI 판단, 미검증).

### 백업과 복원 (3단계 게이트)
- `radar backup`은 표마다 `COPY ... TO STDOUT`(CSV)로 `backups/<시각>/` 아래 파일을 만들고, `manifest.json`에 표별 행 수와 파일 SHA-256을 적는다. `backups/`는 git에서 뺀다.
- `radar restore <폴더>`는 운영 스키마를 건드리지 않고, 새 임시 스키마에 마이그레이션을 적용한 뒤 `COPY ... FROM STDIN`으로 되살리고, 표별 행 수와 내용 체크섬을 manifest와 비교해 결과를 출력한다. 운영으로 되돌리는 일은 자동으로 하지 않는다(되돌리기 어려운 작업이라 사람이 한다).

### 3단계 시험 (게이트와 대응)
- 출처 연결률: 출처 없는 기술 0건(`technologies_without_source`).
- 별칭 검색: 한글·영문 별칭으로 찾아도 같은 기술 한 줄.
- 백업 복원: 기술·이벤트·메모의 행 수와 체크섬이 같다.
- 분석 실패 원인이 Monitor에 보인다.
- 안전: 사설 주소·`file:` URL 읽기 거절, `Host`·`Origin` 위반 요청 거절, `javascript:` 링크가 링크로 나오지 않음, 지시문을 심은 페이지 본문으로 프로필을 만들어도 스키마를 벗어나지 않음.
- 보관한 이름의 새 글이 새 기술을 만들지 않음, 이벤트 재수집 시 중복 없음.

## 승인 시 함께 확인할 가정
1. 제목 300자, 발췌 280자 절단과 `content_hash` 입력 정의.
2. 기본 수집 주기(GitHub 6시간, Hacker News와 RSS 1시간)와 재시도(최대 3번, `2^attempts`분 대기).
3. 퍼지 유사도 0.6과 후보 5개는 시작값이고 골든셋으로 조정한다.
4. 스타 스냅샷을 `metadata`에 두고 별도 테이블은 만들지 않는다.
5. (2단계) 사전 필터는 제외 규칙 없이 시작하고, 일일 상한에 걸릴 때 신호 규칙을 넣는다.
6. (2단계) `confidence`는 항상 `Unverified`이고 `evidence_type`은 소스 종류로 정한다(GitHub 저장소는 `official`로 두지만 공식 저장소인지는 확인하지 않은 값이다).
7. (2단계) 별칭은 모델이 영문·한글로 제안하고, 한글 별칭의 정확도는 골든셋에서 재지 않는다.
8. (2단계) 보류 큐 명령 4개(`list`, `set`, `link`, `new`)만 두고 화면은 3단계에서 만든다.
9. (2단계) 골든셋 평가는 한 번에 하루 호출의 20%를 쓰고, 평가 중에는 운영 워커를 멈춘다.
10. (2단계) 한 글이 기술 여러 개를 다루면 대표 하나만 다룬다(골든셋 86번 사례).
