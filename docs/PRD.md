# Tech Radar Agent — PRD v1.1

Nov 5, 2026 · @YsOmar

## 문서 개요와 v1.0 대비 변경점

v1.1은 Tech Radar Agent를 6가지 역량으로 나눠 한 단계씩 완성하도록 v1.0을 다시 짠 PRD다. 6가지 역량은 수집 엔진, 기술 식별, 지식 데이터베이스, 관계 분석, 브리핑, 시각화이고, 개발 순서도 이 순서를 따른다.

- 상태: Approved(2026-11-05). v1.0을 대체한다. 남은 열린 질문은 4단계에서 측정할 관계 Precision 목표치뿐이다.
- 해석 전제: "6가지 기술"을 v1.0 마지막 장의 6단계 개발 순서, 곧 6가지 제품 역량으로 읽었다. 6개 엔티티 유형은 지식 모델의 분류 체계로 이 역량과는 별개이며, 유형을 여는 순서는 구현 가설로 따로 둔다. 의도와 다르면 이 절부터 고친다.
- 제품 유형: 개인형 기술 인텔리전스 플랫폼. 핵심 가치는 Knowledge.

| 항목 | v1.0 | v1.1 |
| --- | --- | --- |
| 구성 | 4주 단위 Phase 1\~4 | 6개 역량 단계, 단계마다 게이트(완료 기준) |
| 기술 유형 | 자유 문자열 `technology_type` | 6개 유형 enum, 단계별로 도입 |
| 상태 | 성숙도·생애주기가 한 덩어리 | 성숙도, 생애주기, `archived_at`을 분리. 신뢰도는 주장·관계·출처 연결 단위 |
| 변화 이력 | 최신 값으로 갱신 | `technology_events`로 시점별 보존 |
| 중복 방지 | URL·해시 규칙 | 규칙 → 퍼지 → LLM 순 매칭, 후보 사전 필터 |
| 보안 | 선언만 있음 | 입력·출력 검증을 수용 기준에 포함 |
| 범위 | 전체 기술 분야 | 초기에는 소프트웨어·AI. 스파이크 결과로 확정 |

## 비전과 점진적 구축 원칙

각 단계는 앞 단계 위에서 혼자서도 쓸모가 있어야 하고, 게이트를 통과해야 다음 단계를 시작한다. 제품 철학은 v1.0과 같은 Discover → Understand → Connect → Remember다.

성공 기준: 사용자가 직접 검색하지 않아도 중요한 기술 변화를 놓치지 않고, 과거에 발견한 기술과 새 기술의 관계를 이해할 수 있어야 한다.

철학과 단계의 대응은 이렇다. Discover는 1단계, Understand는 2단계, Remember는 3단계, Connect는 4단계다. 5\~6단계는 쌓인 지식을 사용자에게 돌려주는 전달 단계다.

1. 단계 게이트: 이전 단계의 완료 기준을 통과하기 전에는 다음 단계를 시작하지 않는다.
2. 데이터 먼저, 화면과 에이전트는 나중: 데이터 모델과 중복 탐지가 확정되기 전에는 프론트엔드와 AI 에이전트를 만들지 않는다.
3. 매 단계 끝에 쓸 수 있는 결과물이 남는다. 1단계는 수집 로그와 원본 데이터, 3단계는 검색 가능한 지식 DB다.
4. AI는 규칙으로 안 되는 곳에만 쓴다. URL·해시 중복 검사는 규칙이고, 기술 후보 추출·분석·관계 추출이 AI 몫이다.
5. 테스트는 단계마다 실제 데이터 fixture로 만든다. 마지막 주에 몰지 않는다.
6. 사실과 AI 생성 설명을 섞지 않는다. 중요한 주장에는 출처를 붙인다.

## 문제 정의, 대상 사용자, 비목표

기술 정보는 여러 플랫폼에 흩어져 있고, 읽고 나면 지식으로 남지 않는다. 이 제품은 발견한 기술을 시간이 지날수록 깊어지는 개인 지식으로 쌓는다.

**해결하려는 문제**

- 정보가 여러 플랫폼에 분산되어 있다.
- 기술의 등장 시점과 발전 흐름을 추적하기 어렵다.
- 유사하거나 파생된 기술 사이의 관계를 알기 어렵다.
- 뉴스 소비로 끝나 지식이 축적되지 않는다.
- 과거에 접한 기술의 맥락을 다시 찾기 어렵다.

**대상 사용자**

여러 분야의 새 기술을 꾸준히 학습하려는 개인 1명. MVP는 단일 사용자로 운영하되, 이후 확장 비용을 줄이려고 처음부터 `user_id`를 둔다.

**비목표 (MVP에서 만들지 않는다)**

- 공개형 SaaS와 다중 사용자 관리
- 기술의 미래를 예측하는 AI
- AI가 코드를 실행하거나 시스템을 바꾸는 기능
- 모든 기술의 실시간 모니터링
- 자동 실험·벤치마킹, 소셜 기능

## 단계별 요구사항

각 단계는 목표, 요구사항, 완료 기준, 범위 밖을 갖는다. 완료 기준이 곧 다음 단계로 가는 게이트다. 수치는 v1.0의 초기 목표를 가져왔고 스파이크와 골든셋 결과로 조정한다.

### 1단계 · 수집 엔진 (Discover)

목표: 사용자가 찾지 않아도 원본 콘텐츠가 중복 없이 쌓인다.

| ID | 요구사항 |
| --- | --- |
| S1-01 | GitHub(신규 저장소, 시드 저장소 릴리스), Hacker News, RSS 3개 어댑터를 공통 인터페이스로 구현한다. |
| S1-02 | 원본 URL, 최초 발견 시각, 수집 시각을 보존한다. |
| S1-03 | URL을 정규화하고 제목·본문을 정제한다. 정규화 규칙은 스파이크에서 관찰한 사례로 정한다. |
| S1-04 | 중복 방지 키 `external_id`, `normalized_url`, `content_hash`를 각각 별도 제약으로 둔다. `external_id`가 없는 소스(RSS 등)도 중복되지 않아야 한다. |
| S1-05 | 출처별 수집 주기를 설정하고, 모든 실행과 실패 원인을 `collection_runs`에 기록한다. 실패한 수집은 재실행할 수 있다. |
| S1-06 | 본문 전문은 저장하지 않는다. 제목, URL, 짧은 발췌, 메타데이터만 저장한다. |
| S1-07 | 작업은 PostgreSQL 잡 테이블과 워커 1개로 실행한다. |

**완료 기준 (게이트)**

- 3개 소스에서 실제 데이터를 수집하고 수집 성공률이 95% 이상이다. 성공률은 소스별 요청 단위로 세며, API 장애는 실패로, 정상적인 빈 결과는 성공으로 본다.
- 같은 URL을 다시 수집하면 기존 행이 갱신되고 새 행이 생기지 않는다.
- 수집 실패의 원인을 로그에서 확인할 수 있다.
- 수집기마다 fixture 테스트가 있다.

**범위 밖**: AI 호출, 기술 엔티티 생성, 사용자 화면(운영용 로그 조회 제외).

### 2단계 · 기술 식별 (Understand)

목표: 수집 항목에서 기술 후보를 골라 정규명, 유형, 별칭을 붙인다.

| ID | 요구사항 |
| --- | --- |
| S2-01 | 규칙 기반 사전 필터(스타 증가율, 토픽, 키워드, 릴리스 여부)를 통과한 항목만 LLM에 보낸다. |
| S2-02 | 항목을 ENTITY(신규 기술), UPDATE(기존 기술 변경), USAGE, NEWS, OPINION, NOISE로 분류한다. |
| S2-03 | 정규명과 별칭을 한·영으로 관리한다(언어 정책은 ADR-005). 유형은 이 단계에서 PRODUCT, FRAMEWORK\_LIBRARY 두 가지부터 쓴다. 유형을 정하지 못하면 유형을 비워 두고 분류 보류 큐에서 사람이 판정한다. |
| S2-04 | 기존 기술과의 매칭을 규칙(정규명·저장소) → 퍼지(`pg_trgm`, 별칭 포함) → LLM 판정 순으로 수행한다. 별칭 일치만으로는 확정하지 않는다(2026-11-06 결정, SPEC v1.3). |
| S2-05 | AI 분석마다 모델, 시각, 입력 해시를 `analysis_runs`에 기록하고 결과를 덮어쓰지 않는다. |
| S2-06 | 외부 콘텐츠를 신뢰할 수 없는 데이터로 다룬다. 분석 모델에 도구 권한을 주지 않고, 출력은 JSON 스키마로 검증한다. |
| S2-07 | 골든셋은 튜닝용과 보류용으로 나눈다. 프롬프트와 규칙은 튜닝용으로만 고치고, 게이트는 건드리지 않은 보류용으로 판정한다. |

**완료 기준 (게이트)**

- 보류용 골든셋에서 후보 판별(Precision·Recall), 유형 분류, 기존 기술 매칭(Precision)이 각각 목표치 이상이다. 목표치는 초기 가설 85%이며 측정 뒤 항목별로 정한다.
- 중복 기술 생성률이 5% 이하다.
- AI 분석 실패가 재시도 가능한 상태로 기록된다.
- 지시문을 심은 fixture 입력에서도 출력이 스키마를 벗어나지 않고, 분석 모델이 도구를 호출하지 않는다.

**범위 밖**: 관계 추출, 기술 상세 프로필 전체 생성, 브리핑.

### 3단계 · 지식 데이터베이스 (Remember)

목표: 식별된 기술이 출처와 함께 영속적인 지식으로 쌓이고, 검색해서 다시 꺼낼 수 있다.

| ID | 요구사항 |
| --- | --- |
| S3-01 | 기술 프로필에 한 줄 설명, 상세 설명, 해결하려는 문제, 주요 특징, 기존 기술과의 차이, 활용 사례, 장점과 한계, 공식 출처를 담는다. 확인하지 못한 정보는 추측하지 않고 "미확인"으로 표시한다. |
| S3-02 | 성숙도, 생애주기, `archived_at`을 별도 컬럼으로 관리한다. 정의는 지식 모델 절에 있다. |
| S3-03 | 신뢰도(Verified, Corroborated, Unverified, Disputed)를 주장(claim) 단위로 기록하고 근거 출처를 연결한다. |
| S3-04 | `technology_events`에 최초 공개, 릴리스, 인수, 통합, 지원 종료를 시점과 함께 쌓는다. 같은 이벤트는 재수집해도 중복되지 않는다. 3단계는 최초 공개와 릴리스만 규칙으로 쌓고, 인수·통합·지원 종료는 5단계(S5-07)로 미뤘다(2026-11-08 결정, 2026-11-09 다시 미룸). |
| S3-05 | 사용자별 지식 상태(unread, saved, learned), 메모, 중요도를 `user_id`와 함께 저장한다. AI 생성 지식과 개인 메모는 분리한다. |
| S3-06 | URL로 기술을 수동 등록할 수 있다. 이미 아는 기술 50\~100개를 넣어 지식 그래프의 시작 데이터로 쓴다. |
| S3-07 | 기술명, 별칭, 키워드 검색과 카테고리·출처·기간 필터를 지원한다. |
| S3-08 | 웹 화면은 Discovery Feed, Knowledge Base(검색·상세·메모), System Monitor 3개만 만든다. |
| S3-09 | 유형을 PROTOCOL\_STANDARD, MODEL까지 넓힌다. |

**완료 기준 (게이트)**

- 기술 하나에 서로 다른 출처 3개를 연결해 보여준다. 출처 연결률은 100%다.
- 별칭으로 검색해도 같은 기술이 나온다.
- DB 백업을 복원하면 기술, 이벤트, 개인 메모가 그대로 돌아온다.
- 분석 실패의 원인을 System Monitor에서 확인할 수 있다.

**범위 밖**: 관계 그래프, 브리핑, 시각화.

### 4단계 · 관계 분석 (Connect)

목표: 기술 사이의 관계를 근거와 함께 쌓아, 새 기술이 기존 지식과 연결된다.

| ID | 요구사항 |
| --- | --- |
| S4-01 | 관계 유형은 DERIVED\_FROM, BUILT\_ON, EXTENDS, IMPLEMENTS, PART\_OF, REPLACES, COMPETES\_WITH, INTEGRATES\_WITH, RELATED\_TO를 쓴다. |
| S4-02 | 방향은 "주어가 source"로 통일한다. REPLACES는 신형 → 구형이다. 대칭 관계는 id 순서로 정렬해 한 방향만 저장한다. |
| S4-03 | 유형 조합별 허용 관계 매트릭스를 둔다. AI가 제안한 관계가 매트릭스를 어기거나 유형 없는 기술이 끼면 저장하지 않고 검토 목록(System Monitor, 보류 큐 옆)으로 보낸다. 유형을 고치면 다시 검사하고, 버리기도 할 수 있다(2026-11-09 결정). |
| S4-04 | 관계마다 근거를 여러 개 연결하고 AI 판단의 신뢰도를 기록한다. 사용자의 확인 여부(user\_verified)는 신뢰도와 별개 필드로 기록하며, 확인 전까지는 false다. |
| S4-05 | 5단계(S5-08)로 미뤘다(2026-11-09 결정, 4단계는 관계와 그래프에 집중). |
| S4-06 | 기술 상세 화면에 관련 기술 목록을 보여주고 이동할 수 있게 한다. |
| S4-07 | 5단계(S5-07)로 미뤘다(2026-11-09 결정). |
| S4-08 | Knowledge Graph 화면: 기술을 점으로, 근거가 있는 관계를 선으로 그리고, 점을 누르면 기술 상세로 간다(옵시디언 그래프뷰처럼). 6단계의 S6-02를 이 단계로 당겼다(2026-11-09 사용자 결정, 핵심 기능). |

**완료 기준 (게이트)**

- 허용 매트릭스를 위반한 관계가 저장되지 않는다.
- AI가 뽑은 모든 관계에 근거가 1개 이상 있다. 사용자가 직접 이은 관계는 사용자가 근거다(2026-11-09 결정).
- AI 관계 무작위 50개를 사용자가 화면에서 확인·숨김으로 판정해 Precision(확인 ÷ 판정)을 잰다. 목표치는 측정 뒤에 정한다(2026-11-09 결정).
- Knowledge Graph 화면의 점과 선이 DB의 기술·관계와 일치한다(표본 수동 검수, S4-08).

**범위 밖**: 레이더·타임라인 시각화(6단계), 영향 분석, 예측.

### 5단계 · 브리핑

목표: 사용자가 접속하지 않아도 일간·주간 브리핑이 만들어진다.

| ID | 요구사항 |
| --- | --- |
| S5-01 | 일일 브리핑에 신규 기술, 주목할 기술, 기존 기술의 주요 업데이트, 관심 기술과 관련된 새 발견, 원본 출처 링크를 담는다. |
| S5-02 | 주간 브리핑에 한 주의 주요 변화, 신규 기술, 관심 분야별 변화, 기존 기술의 발전 흐름, 관찰 목록을 담는다. |
| S5-03 | 관찰 목록(Watchlist)은 규칙 기반으로 만든다. 저장한 기술의 새 릴리스, 관련 기술의 등장처럼 근거가 있는 변화만 올리고 미래를 예측하지 않는다. |
| S5-04 | `briefing_items`에 어떤 변화(이벤트 또는 수집 항목)가 어느 브리핑에 실렸는지 기록한다. 중복 판정은 기술 단위가 아니라 변화 단위로 하므로, 같은 기술의 새 릴리스는 다시 싣고 같은 변화의 반복만 막는다. |
| S5-05 | 전달 채널은 웹 대시보드의 Briefings 화면이다. 이메일·슬랙은 후속으로 둔다. |
| S5-06 | 스케줄러가 브리핑을 자동 생성하고, 실패는 기록하며 재실행할 수 있다. |
| S5-07 | (4단계 S4-07에서 옮김) 글에서 인수·통합·지원 종료 이벤트를 뽑고, 인수·통합 이벤트가 관계 생성 후보가 되도록 잇는다. |
| S5-08 | (4단계 S4-05에서 옮김) 유형을 PATTERN\_CONCEPT, RESEARCH까지 넓힌다. 경계가 모호한 유형이라 관계로 위치를 잡을 수 있게 된 뒤에 열고, ADR-0001 판정 규칙과 ADR-0002 매트릭스 행을 먼저 정한다. |

**완료 기준 (게이트)**

- 일일·주간 브리핑이 자동 생성되고 생성 성공률이 95% 이상이다.
- 같은 변화는 이전 브리핑에 실렸으면 다시 싣지 않고, 같은 기술의 새 변화는 다시 싣는다.
- 모든 항목에 원본 출처 링크가 있다.
- 골든셋에서 중요 변화로 표시한 항목이 수집 → 분석 → 브리핑까지 도달한 비율(도달률)을 측정한다. 목표치는 측정 뒤에 정한다.

**범위 밖**: 이메일·슬랙 전달, 개인화 추천.

## 지식 모델

기술 엔티티는 6개 유형으로 제한하고, 유형은 단계마다 나눠 연다. 도입 순서는 가설이며 스파이크의 S1·S1b 결과로 확정한다.

### 엔티티 유형

| 유형 | 정의 | 예 | 도입 |
| --- | --- | --- | --- |
| PRODUCT | 사용자가 직접 쓰는 제품·서비스 | Claude Code | 2단계 |
| FRAMEWORK\_LIBRARY | 개발에 가져다 쓰는 프레임워크·라이브러리 | LangChain, Next.js. PRODUCT와의 경계는 스파이크에서 확인 | 2단계 |
| PROTOCOL\_STANDARD | 여러 구현이 따르는 프로토콜·표준 | MCP | 3단계 |
| MODEL | 공개된 모델·모델 계열 | 모델 카드가 있는 공개 모델 계열 | 3단계 |
| PATTERN\_CONCEPT | 구현과 무관한 아키텍처 패턴·개념 | RAG | 4단계 |
| RESEARCH | 논문이 제안한 기법·결과 | 논문 원문이 아니라 그 논문이 제안한 기법 | 4단계 |

- 저장소와 논문 원문은 기술 엔티티가 아니라 수집 항목(`source_items`)이다. `technology_sources`는 기술과 수집 항목을 잇는 연결 테이블이고, `evidence_type`으로 연결의 성격을 구분한다.
- 기술 하나의 유형은 하나다. 판정이 애매하면 유형을 비워 두고 분류 보류 큐에서 사람이 판정한다. 보류는 유형 값이 아니라 상태다.

### 데이터 흐름과 개념 구분

수집 항목 하나가 기술 하나에 대응하지는 않으므로 네 개념을 구분한다. 수집 항목과 기술은 다대다이고 `technology_sources`가 잇는다.

| 개념 | 예 | 역할 | 저장 |
| --- | --- | --- | --- |
| 출처 제공자 | GitHub, arXiv, RSS 발행처 | 데이터를 제공하는 플랫폼 | `sources` |
| 수집 항목 | 저장소, 논문, 게시글 | 수집한 개별 콘텐츠 | `source_items` |
| 기술 | MCP, RAG, Claude Code | 지식으로 관리하는 기술 | `technologies` |
| 근거 | 수집 항목의 특정 내용 | 주장과 관계를 뒷받침 | `technology_sources`, `relation_evidence` |

흐름은 수집 항목 → 기술 → 근거 → 주장 → 관계 → 사용자 지식이다.

공통 데이터(기술, 수집 항목, 관계)와 사용자별 데이터를 나눈다. 사용자별 데이터는 `user_knowledge`, 메모, 브리핑, `briefing_items`이며 모두 `user_id`를 가진다. 사용자별 제약은 `UNIQUE (user_id, technology_id)`처럼 `user_id`를 포함한다. 테이블 정의는 DDL 단계에서 확정한다.

### 상태와 신뢰도

성숙도가 낮다고 정보가 부정확한 것은 아니고, 안정된 기술이라고 모든 정보가 검증된 것도 아니므로 두 축을 분리한다.

| 축 | 값 | 붙는 단위 |
| --- | --- | --- |
| 성숙도 `maturity` | experimental, emerging, stable, mature | 기술 |
| 생애주기 `lifecycle_status` | active, maintenance, deprecated, end\_of\_life, unknown | 기술 |
| 보관 `archived_at` | 시스템이 기술을 보관 처리한 시각. 비어 있으면 보관 아님. GitHub 저장소의 archived 상태와는 별개다 | 기술 |
| 신뢰도 | Verified, Corroborated, Unverified, Disputed | 주장(claim), 관계, 출처 연결 |

- 신뢰도는 AI가 판단한 근거의 강도다. 사용자가 확인했는지(`user_verified`)는 신뢰도와 별개 필드로 기록한다.

### 관계 유형과 방향

| 관계 | "A 관계 B"의 뜻 | 대칭 |
| --- | --- | --- |
| DERIVED\_FROM | A는 B에서 파생되었다 | 아니오 |
| BUILT\_ON | A는 B를 기반으로 만들어졌다 | 아니오 |
| EXTENDS | A는 B의 기능을 확장한다(플러그인 → 플랫폼) | 아니오 |
| IMPLEMENTS | A는 프로토콜·표준 B를 구현한다 | 아니오 |
| PART\_OF | A는 B의 하위 구성요소다 | 아니오 |
| REPLACES | 신형 A가 구형 B를 대체한다 | 아니오 |
| COMPETES\_WITH | A와 B는 경쟁한다 | 예 |
| INTEGRATES\_WITH | A와 B는 서로 통합된다 | 예 |
| RELATED\_TO | 위 어디에도 맞지 않는 일반 관련 | 예 |

- 저장된 모든 관계에서 `source_technology_id`가 주어다. 대칭 관계는 id가 작은 쪽을 source로 한 줄만 저장한다.
- 근거는 `relation_evidence`에 여러 개 연결한다. 관계마다 신뢰도를 기록한다.
- 유형 조합별 허용 매트릭스로 AI가 제안한 관계를 검증한다. 예를 들어 IMPLEMENTS는 대상이 PROTOCOL\_STANDARD일 때만 허용한다.
- AI가 연관성을 찾았다는 이유로 파생이나 의존 관계로 확정하지 않는다. 근거가 약하면 RELATED\_TO로 두고 검증 대상으로 남긴다.

### 변화 이력 (`technology_events`)

기술의 최신 정보만 갱신하면 과거 지식이 사라지므로, 변화는 이벤트로 시간순 축적한다. 이벤트 유형 초안은 first\_published, release, acquisition, integration, deprecation, end\_of\_life이며, 스파이크 S4에서 관찰한 값으로 확정한다.

- 시점은 `occurred_at`과 `date_precision`(day, month, year)으로 나눠 저장한다. 공개 시점이 "어느 해 가을"처럼 대략적인 경우가 많기 때문이다.
- 같은 이벤트는 재수집해도 중복되지 않는다. `(technology_id, event_type, occurred_at, evidence_key)`에 unique 제약을 둔다. 근거 키는 릴리스 태그나 공지 URL이다.
- `technologies.first_published_at`은 이벤트에서 파생한 캐시 값이다. 진실의 원천은 이벤트다.
- 이벤트는 고쳐 쓰지 않고 쌓는다.

## 데이터·AI 원칙과 보안

지식이 오염되지 않게 하는 핵심은 출처 보존, 사실과 AI 생성물의 분리, 외부 콘텐츠를 믿지 않는 것이다.

**데이터**

- 모든 수집 항목에 원본 URL과 최초 발견 시각을 보존한다. 최초 공개 시각과 최초 발견 시각은 구분한다.
- AI 분석 결과는 덮어쓰지 않고 이력으로 남기며, 현재 값은 `is_current`로 표시한다.
- 개인 메모와 AI 생성 지식을 구분해 저장한다.
- 삭제보다 보관(`archived_at`)을 우선한다.
- 출처별 지표(스타 증가, 인용 수 등)는 원래 의미를 유지하고 하나의 점수로 합산하지 않는다.

**AI**

- 확인할 수 없는 정보는 추측하지 않고 "미확인"으로 표시한다.
- 중요한 주장에는 근거 출처를 연결하고, 분석마다 생성 시각과 모델 정보를 기록한다.
- AI 공급자는 인터페이스 뒤에 두어 특정 공급자에 묶이지 않게 한다.
- 토큰 사용량과 API 비용을 기록한다.

**보안 (프롬프트 인젝션 방어)**

- 외부 콘텐츠는 신뢰할 수 없는 데이터다. 본문에 섞인 지시문이 분석 동작을 바꿀 수 있다.
- 분석 모델에는 도구 권한(파일, 네트워크, 코드 실행)을 주지 않는다.
- 출력은 JSON 스키마로 검증하고, 어기면 저장하지 않고 실패로 기록한다.
- 입력 HTML은 정제한다.
- 위 규칙은 2단계 게이트에서 지시문을 심은 fixture로 검증한다.

**저작권과 약관**

- 본문 전문은 저장하지 않는다. 제목, URL, 짧은 발췌, 메타데이터 중심으로 저장한다.
- 출처를 추가할 때마다 해당 API의 이용 약관을 확인한다.

**운영**

- 비동기 작업은 PostgreSQL 잡 테이블과 워커 1개로 시작한다. 모든 작업의 상태, 오류, 재시도를 기록하고 재실행할 수 있다.
- 외부 API가 장애여도 저장된 지식은 조회할 수 있어야 한다.
- 백업과 복구를 지원하고, 복원 결과를 검증한다.

## 단계별 성공 지표

단계 게이트는 아래 지표로 판정한다. 수치는 v1.0의 초기 목표이고, 실제 운영 데이터로 조정한다. 표본이 60건 안팎이면 임계값 근처에서 ±10%p 정도 흔들리므로, 그럴 때는 표본을 늘려 다시 잰다.

v1.0의 "기술 식별 정확도 85%"는 후보 판별, 유형 분류, 기존 기술 매칭 세 항목으로 나눴다. 같은 85%를 초기 가설로 두되 측정 뒤 항목별로 정한다. 2단계 지표는 튜닝에 쓰지 않은 보류용 골든셋으로 잰다.

| 단계 | 지표 | 목표 | 측정 방법 |
| --- | --- | --- | --- |
| 1 | 연동 데이터 소스 | 3개 이상 | 활성 소스 수 |
| 1 | 소스별 수집 성공률 | 95% 이상 | 소스별 요청 단위의 성공 대비 전체. API 장애는 실패, 정상적인 빈 결과는 성공 |
| 1 | 재수집 시 새로 생긴 중복 행 | 0 | 같은 입력을 두 번 수집해 fixture로 비교 |
| 2 | 후보 판별 Recall | 85% 이상(2026-11-08 Recall 우선 결정) | 보류용 골든셋 |
| 2 | 후보 판별 Precision | 75% 이상(2026-11-08 결정) | 보류용 골든셋 |
| 2 | 유형 분류 정확도 | 80% 이상(2026-11-08 결정. 유형 오류는 보류 큐에서 고칠 수 있고 중복을 만들지 않는다) | 보류용 골든셋 |
| 2 | 기존 기술 매칭 Precision | 측정 후 설정(초기 가설 85%) | 보류용 골든셋 |
| 2 | 중복 기술 생성률 | 5% 이하 | 보류용 골든셋에서 같은 기술이 둘 이상 생긴 비율 |
| 3 | 출처 연결률 | 100% | 출처가 없는 기술 수가 0 |
| 3 | 백업 복원 | 기술·이벤트·메모 전부 복원 | 복원 전후 행 수와 체크섬 비교 |
| 4 | 근거 없는 관계 | 0건 | `relation_evidence`가 없는 관계 수 |
| 4 | 허용 매트릭스 위반 관계 | 0건 | 검증 쿼리 |
| 4 | 관계 Precision | 측정 후 설정 | 골든셋 관계 표본 |
| 5 | 브리핑 생성 성공률 | 95% 이상 | 생성 시도 대비 성공 |
| 5 | 출처 없는 브리핑 항목 | 0건 | 항목별 출처 링크 검사 |
| 5 | 중요 변화 도달률 | 측정 후 설정 | 골든셋에서 중요 변화로 표시한 항목 중 수집 → 분석 → 브리핑에 도달한 비율 |
| 6 | 화면과 DB의 불일치 | 0건 | 표본 수동 검수 |

## 일정과 위험

MVP(1\~3단계)는 사전 작업 약 1주를 포함해 총 4\~5주로 잡고, 4\~6단계는 그 위에 이어 붙인다. 기간은 초기 추정이며 스파이크가 끝나면 다시 잡는다.

**사전 작업 (약 1주)**

1. 수집 스파이크(1\~2일): GitHub·Hacker News·RSS 원본 샘플 수집과 수동 라벨링.
2. 범위·엔티티·관계 확정: ADR-001, ADR-002와 PRD 범위 절.
3. DDL v1.1: PostgreSQL에서 제약조건과 인덱스를 검증.
