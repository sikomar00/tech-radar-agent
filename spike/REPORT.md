# 수집 스파이크 결과 (2026-11-05)

## 한 일과 한계
- `spike/collect.py`(표준 라이브러리, 읽기 전용)로 호출 45회, 실패 0회. 샘플은 `spike/samples/`에 있다(제목, URL, 짧은 발췌, 메타데이터만).
- 건수: GitHub 45(신규 저장소 30, 시드 5개의 릴리스 15), Hacker News 30, RSS 160(피드 7개).
- 한계: 수동 라벨링은 하지 않았다(사전 작업 4의 골든셋 단계). 표본이 작고 최근 7일치이며, API 장애 상황은 만나지 못했다.

## 약관·한도 확인
- GitHub: REST 비인증 한도는 시간당 60회(공식 문서). 이번 실행은 검색 6회와 릴리스 5회였고 한도 안이었다. ToS H절에는 데이터 저장·재배포 제한 규정이 없고, 스팸 목적 사용과 사용자 개인정보 판매를 금지한다. 시드 저장소가 늘면 한도가 모자랄 수 있어 ADR-003(수집 전략)에서 정한다.
- Hacker News 공식 API: "속도 제한 없음"이 명시돼 있다. 이용 약관 문서는 없다.
- Algolia HN Search: 문서 페이지를 읽지 못해 약관과 한도를 확인하지 못했고, 사용하지 않았다.
- RSS: 발행처별 약관은 확인하지 못했다. 소스를 추가할 때마다 확인해야 한다.

## 관찰
1. **교차 소스 중복**: 같은 URL이 6건 겹쳤다. HN API와 hnrss 미러 5건, hnrss와 개인 블로그 1건이다. HN 미러 피드는 소스로 쓰지 않는다.
2. **URL 정규화**: 정규화 전후의 중복 수가 같아서(6건) 이 표본으로는 규칙을 정할 수 없다. 끝 슬래시, 추적 파라미터 같은 변형 사례가 표본에 없다. 정규화 규칙은 일반 관행에 따른 가설이고, 사례가 나오면 보완한다.
3. **external_id**: GitHub와 HN은 숫자 id가 있다. RSS는 guid가 있지만 140/160만 URL이고 Cloudflare 20건은 URL이 아니다. id 형식이 소스마다 달라 `external_id`는 소스별로 해석해야 한다.
4. **발췌 없음**: Hugging Face 피드 30건 전부 발췌가 비어 있다. 발췌가 없는 항목을 허용해야 하고, 이때 `content_hash` 입력은 제목과 URL뿐이다.
5. **GitHub 신규 저장소**(최근 7일, 스타 20 초과, 상위 30): 토픽이 있는 것 14/30, 중국어 설명 6/30, 설명 없음 2/30이다. 상위권에 Claude Code 스킬·플러그인류가 많다. 스타는 절대값만 있어서 "스타 증가율"(S2-01)을 쓰려면 같은 저장소를 두 번 이상 수집해야 한다.
6. **릴리스 태그**: langchain 저장소는 `langchain-core==1.7.6`, `langchain==1.4.9`, `langchain-typesafe==0.0.1`처럼 패키지별 태그를 쓴다. 저장소 하나가 기술 하나가 아니다.
7. **Hacker News**: 30건 중 URL이 없는 글이 1건이다. 모델 가중치 공개(MODEL 후보)와 제품 발표가 섞여 있다.
8. **비소프트웨어 피드**: IEEE Spectrum 30건과 NASA 10건의 제목을 보면 기술 후보로 볼 만한 것은 7건 안팎이다(전기 비행, 시뮬레이션 앱, 양자 소재, RF 신호발생기, X-70 실험기, 위성 중계, 항법 실험). 나머지는 뉴스, 인물, 이미지, 논평이다. 6개 유형에 깔끔하게 맞는 것은 거의 없고 RESEARCH 성격이 일부 있다. IEEE Spectrum도 상당수가 AI 관련이다.

## 결론
- 초기 범위는 소프트웨어·AI로 한정한다(관찰 8).
- 기술 엔티티 모델은 ADR-001, 관계 모델은 ADR-002로 정리했다.
